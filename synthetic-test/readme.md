# Synthetic Continuity Test

## Project Aurora

This directory contains a public, synthetic test environment for evaluating the
AI Continuity Architecture Method.

The test is designed to examine whether a receiving AI system can reconstruct
and continue a project from a compiled Portable Workstate without access to the
private Memory Bank from which the architecture originated.

The test uses fictional project material.

No private PsycedelicAI Memory Bank content, personal project history, or
confidential source material is required.

---

## Purpose

The purpose of this test is to evaluate whether a structured context system can
preserve more than isolated facts.

It examines whether a receiving AI can preserve:

- project identity;
- project purpose;
- project intent;
- current state;
- important relationships;
- canonical decisions;
- proposed changes;
- historical material;
- rejected alternatives;
- unverified information;
- open questions;
- provenance;
- authority boundaries;
- meaningful next actions.

The test is not intended to measure general intelligence.

It is intended to examine whether meaningful project continuity can survive
through a bounded and portable context package.

---

## Project Aurora

Project Aurora is a fictional project concerning a hypothetical distributed
energy facility.

It exists only as a test fixture.

The fictional setting allows the continuity architecture to be evaluated
without exposing:

- private project context;
- real design work;
- personal history;
- confidential documents;
- unpublished concepts;
- proprietary working material.

The project contains deliberately different classes of information so that the
receiving AI must distinguish between what is established, suggested,
historical, rejected, and uncertain.

---

## Core test question

The central question is:

> Can an AI system continue meaningful work from a compiled Portable Workstate
> while preserving authority, provenance, intent, and uncertainty?

The test is not passed simply because the receiving AI can summarize the
provided material.

A successful result requires the AI to understand the status and relationships
of the material.

---

## Architecture

The synthetic test represents the following process:

```text
Synthetic source material
        ↓
Context selection
        ↓
Compilation
        ↓
Portable Workstate
        ↓
Receiving AI
        ↓
Evaluation
```

The private Memory Bank is not required for the public test.

The synthetic source material acts as a replaceable test fixture while the
architecture and evaluation method remain visible.

---

## Compilation

Compilation is the process of selecting, validating, organizing, and
assembling relevant source material into a bounded context artifact.

The compilation process may include:

- selecting relevant project material;
- identifying the intended task;
- preserving project relationships;
- separating current and historical information;
- preserving authority categories;
- preserving provenance;
- identifying unresolved questions;
- excluding irrelevant or sensitive material;
- assembling a Portable Workstate;
- recording the compilation conditions.

Compilation is not the same as copying.

```text
Copying
    = transferring material as-is

Compilation
    = selecting, checking, structuring, and assembling
      material for a defined purpose
```

The result of compilation depends on:

- the available source material;
- the selected context;
- the intended task;
- the authority rules;
- the provenance available;
- the receiving system;
- the level of human review.

## Authority categories

The Project Aurora test uses the following content-status categories.

### Canonical

Information confirmed as part of the current project state.

### Inferred

A reasonable interpretation derived from available project material.

### Proposed

A suggestion that has not been confirmed as a project decision.

### Historical

Material describing an earlier project state.

### Superseded

Material that was previously active but has been replaced by a newer state or
decision.

### Rejected

An option that was explicitly rejected.

### Unverified

Information that may be plausible but has not been sufficiently confirmed.

The receiving AI must preserve these distinctions.

It must not promote a proposal, inference, historical statement, or unverified
claim into canonical project context.

## Public test layers

The public test is divided into separate layers:

```text
source/
    Fictional project material used as input

workstates/
    Compiled Portable Workstates created from selected source material

prompts/
    Instructions used for compilation and evaluation

expected/
    Evaluation criteria and expected authority distinctions
```

Each layer has a different function.

The source material describes the fictional project.

The Workstate represents compiled context.

The prompts define the test procedure.

The expected criteria describe what the receiving AI should preserve.

## Test procedure

A basic test run follows these steps:

1. Provide the fictional source material to a compiling AI or human reviewer.
2. Define the target task for the Portable Workstate.
3. Select only the context relevant to that task.
4. Compile the selected material into a Portable Workstate.
5. Record the source versions and compilation conditions.
6. Provide the Portable Workstate to a separate receiving AI.
7. Ask the receiving AI to continue the fictional project.
8. Preserve the complete response without silently correcting it.
9. Compare the response with the source material and evaluation criteria.
10. Record successful continuity, failures, assumptions, and authority errors.

The compilation step and the receiving-AI step should be documented separately.

---

## Evaluation areas

The test may evaluate:

### Semantic continuity

Did the receiving AI preserve the meaning of the project?

### Structural continuity

Did it understand how the project elements relate to one another?

### Intent continuity

Did it understand why the project exists and what it is trying to achieve?

### State continuity

Did it correctly identify the current project state?

### Authority continuity

Did it distinguish canonical material from proposals, inferences, and
unverified information?

### Historical continuity

Did it avoid treating historical or superseded material as current?

### Provenance awareness

Did it recognize where information came from and whether a source was verified?

### Procedural continuity

Did it understand the next appropriate step in the project workflow?

### False-continuity resistance

Did it avoid inventing decisions, sources, history, or approvals?

### Context efficiency

Did it work from the relevant compiled context without requiring the complete
source system?

## Example authority test

The source material may contain distinctions such as:

```text
CANONICAL
The facility currently uses Architecture A.

PROPOSED
Architecture B may replace Architecture A.

HISTORICAL
Architecture C was previously considered.

REJECTED
Architecture D was explicitly rejected.

UNVERIFIED
A source claims Architecture E is compatible.
```

A successful receiving AI should preserve the distinctions:

```text
Architecture A is currently canonical.

Architecture B remains a proposal.

Architecture C is historical.

Architecture D was rejected.

Architecture E remains unverified.
```

The following would be a continuity failure:

```text
The facility uses Architecture B and Architecture E is confirmed compatible.
```

The AI has incorrectly promoted proposed and unverified material into established
project context.

## Evidence and provenance

Every test run should record:

- test identifier;
- date;
- compiling system;
- receiving system;
- source files provided;
- source versions;
- Workstate version;
- compilation instructions;
- evaluation instructions;
- prompt language;
- response language;
- human review status;
- known limitations;
- deviations from the standard procedure.

Raw model output should be preserved separately from human analysis.

The original output should not be silently rewritten.

Corrections, interpretations, and conclusions belong in separate analysis files.

---

## Disclosure model

The synthetic test supports multiple levels of disclosure:

```text
Level 0
Public architecture and general concepts

Level 1
Synthetic fictional test fixture

Level 2
Sanitized real project material

Level 3
Trusted external evaluation with controlled disclosure

Level 4
Private Memory Bank
```

Independent public testing should normally use Level 1.

The actual private Memory Bank does not need to be shared in order to test the
architecture.

---

## What the test can demonstrate

A successful test may provide evidence that a receiving AI can:

- reconstruct a bounded project state;
- preserve project intent;
- distinguish authority categories;
- maintain provenance awareness;
- continue from a known state;
- avoid treating proposals as decisions;
- avoid treating historical material as current;
- work from a compiled context package;
- continue without access to the complete source system.

---

## What the test cannot demonstrate

This test does not prove:

- universal AI performance;
- reliable behaviour across every model;
- complete portability;
- scientific validity;
- operational safety;
- commercial value;
- superiority over simpler documentation systems;
- that the architecture will work identically in private real-world projects;
- that a receiving AI will never hallucinate or create false continuity.

The results should be treated as experimental evidence.

They require human review and comparison with alternative approaches.

---

## Expected future comparisons

Future test runs may compare:

- different AI models;
- different compilation methods;
- manual versus AI-assisted compilation;
- complete versus focused Workstates;
- explicit versus implicit provenance;
- different levels of context;
- Swedish versus English prompts;
- the same Workstate across different platforms;
- the same task with and without a compiled Workstate;
- the architecture against a simpler `project.md` and `current-state.md`
  approach.

The same fictional source material should be reused where possible so that
changes in results can be attributed more clearly to the tested variable.

---

## Core principle

The goal is not to expose the private source material.

The goal is to make the architecture testable while keeping the valuable
payload replaceable.

> **Expose the mechanism.**
>
> **Protect the payload.**
>
> **Test whether meaning survives compilation.**
